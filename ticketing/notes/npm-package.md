# Complete Guide: Creating, Configuring & Publishing a TypeScript NPM Package

This guide covers everything you need to know about building, structuring, publishing, and updating a shared TypeScript NPM package across microservices.

---

## 1. NPM Account, Organization & Access Token Setup (One-Time Setup)

Before publishing any scoped package (e.g. `@mehul-mrtickets/common`), you must configure your npm account and organization.

### Step 1: Create an NPM Account
1. Go to [https://www.npmjs.com/signup](https://www.npmjs.com/signup) and create your account.
2. Verify your email address.

### Step 2: Create an Organization on npmjs.com
1. Click on your **Profile Icon** in the top-right corner of npmjs.com.
2. Select **Add Organization** from the dropdown.
3. Enter your desired organization name (e.g., `mehul-mrtickets`). This becomes your package scope (`@mehul-mrtickets/...`).
4. Select the **Free Plan** ($0/month with unlimited public packages) and click **Create**.

### Step 3: Generate an NPM Access Token
Because npm enforces 2FA for publishing, using an **Automation Access Token** allows you to publish without 2FA / OTP prompts:
1. Click your **Profile Icon** $\rightarrow$ **Access Tokens** (or visit [https://www.npmjs.com/settings/tokens](https://www.npmjs.com/settings/tokens)).
2. Click **Generate New Token** $\rightarrow$ select **"Classic Token"**.
3. Select the **"Automation"** option (Automation tokens are designed to bypass 2FA for CLI publishing).
4. Click **Generate Token** and copy the token (it begins with `npm_...`).

### Step 4: Authenticate on your Terminal
Log in from your terminal using web authentication:
```powershell
npm login --auth-type=web
```
This opens your browser. Click **Accept / Authorize** to log in your terminal session.

### Step 5: Publishing with the Auth Token
You can either pass the token directly during publish:
```powershell
npm publish --access public --//registry.npmjs.org/:_authToken="YOUR_TOKEN_HERE"
```

Or save it permanently to your machine so you never have to type it again:
```powershell
npm config set //registry.npmjs.org/:_authToken "YOUR_TOKEN_HERE"
```

## 2. Directory & File Structure

```text
common/
├── src/                      # TypeScript source code
│   ├── errors/               # Custom error classes (reusable across services)
│   ├── middlewares/          # Custom express middlewares (reusable across services)
│   └── index.ts              # Entry point: Re-exports all public APIs
├── build/                    # Compiled JavaScript (.js) and Type Definitions (.d.ts)
├── .gitignore                # Files excluded from git
├── package.json              # NPM package metadata, scripts, and dependencies
└── tsconfig.json             # TypeScript compiler settings
```

### Significance of Each File & Folder:

- **`src/`**: The human-readable TypeScript source directory where you write and maintain code.
- **`src/index.ts`**: The single public entry point of the package. It uses `export * from "..."` to expose all error classes and middlewares so consumers can import them easily:
  ```typescript
  import { BadRequestError, currentUser } from '@mehul-mrtickets/common';
  ```
- **`build/`**: The output directory generated by the TypeScript compiler (`tsc`). It contains the compiled CommonJS `.js` files and generated `.d.ts` type definition files.
- **`package.json`**: Defines the package identity, main entry files, scripts, and dependencies.
- **`tsconfig.json`**: Configures how TypeScript compiles `.ts` files into `.js` and generates `.d.ts` type declarations.
- **`.gitignore`**: Prevents build artifacts (`build/`) and dependencies (`node_modules/`) from cluttering your git history.

## 3. Configuring `package.json`

Here is the exact configuration used in our `common` package:

```json
{
  "name": "@mehul-mrtickets/common",
  "version": "1.0.5",
  "main": "./build/index.js",
  "types": "./build/index.d.ts",
  "files": [
    "build/**/*"
  ],
  "publishConfig": {
    "access": "public"
  },
  "scripts": {
    "clean": "del-cli --force ./build/*",
    "build": "npm run clean && tsc",
    "pub": "npm version patch && npm run build && npm publish --access public"
  },
  "keywords": [],
  "author": "",
  "license": "ISC",
  "description": "",
  "devDependencies": {
    "del-cli": "^7.0.0",
    "typescript": "^7.0.2"
  },
  "dependencies": {
    "@types/cookie-session": "^2.0.49",
    "@types/express": "^5.0.6",
    "@types/jsonwebtoken": "^9.0.10",
    "cookie-session": "^2.1.1",
    "express": "^5.2.1",
    "express-validator": "^7.3.2",
    "jsonwebtoken": "^9.0.3"
  }
}
```

### Breakdown of Key Fields:

1. **`name` (`@mehul-mrtickets/common`)**: 
   - A **scoped package name** (`@scope/package-name`). 
   - The scope `@mehul-mrtickets` matches your npm account username or organization.

2. **`version` (`1.0.5`)**:
   - Uses Semantic Versioning (`MAJOR.MINOR.PATCH`).
   - Each time you publish an update, the version **must** be incremented.

3. **`main` (`./build/index.js`)**:
   - Specifies the executable JavaScript entry point when a consumer runs `require('@mehul-mrtickets/common')` or `import ... from '@mehul-mrtickets/common'`.

4. **`types` (`./build/index.d.ts`)**:
   - Tells TypeScript where to find the type definitions so consuming microservices get autocomplete and type checking.

5. **`files` (`["build/**/*"]`)**:
   - Whitelist of files included when published to npm. This ensures you only publish compiled `build/` files, keeping the package size small and clean (excluding `src/`, `tsconfig.json`, etc.).

6. **`publishConfig` (`{ "access": "public" }`)**:
   - By default, npm assumes scoped packages are private (paid). This setting forces the package to be published as public for free.

7. **`dependencies` vs `devDependencies`**:
   - **`dependencies`**: Packages needed at runtime by the consuming service (e.g., `jsonwebtoken`, `express-validator`).
   - **`devDependencies`**: Tools only needed while building the package locally (e.g., `typescript`, `del-cli`).

## 4. Configuring `tsconfig.json`

```json
{
  "compilerOptions": {
    "target": "es2020",
    "module": "commonjs",
    "rootDir": "./src",
    "outDir": "./build",
    "declaration": true,
    "declarationMap": true,
    "sourceMap": true,
    "esModuleInterop": true,
    "forceConsistentCasingInFileNames": true,
    "strict": true,
    "skipLibCheck": true
  },
  "include": ["src/**/*"]
}
```

### Why these settings are critical:

- **`rootDir: "./src"` & `outDir: "./build"`**: Tells `tsc` to read source code from `src/` and output compiled files directly into `build/`.
- **`declaration: true`**: Instructs TypeScript to generate `.d.ts` type definition files alongside the JavaScript files.
- **`module: "commonjs"`**: Compiles modern `import`/`export` syntax into standard Node.js `require()`/`module.exports` for maximum compatibility across Node microservices.
- **`esModuleInterop: true`**: Enables seamless importing of CommonJS modules using ES6 import syntax (`import express from 'express'`).

## 5. Build & Publish Commands Explained

### The Scripts:

```json
"scripts": {
  "clean": "del-cli --force ./build/*",
  "build": "npm run clean && tsc",
  "pub": "npm version patch && npm run build && npm publish --access public"
}
```

### Step-by-Step Command Breakdown:

1. **`npm run clean` (`del-cli --force ./build/*`)**:
   - Uses `del-cli` (a cross-platform deletion tool) to wipe old build files before recompiling.
   - Prevents leftover/deleted files from lingering in the build output.

2. **`npm run build` (`npm run clean && tsc`)**:
   - Cleans the `build/` folder first, then runs the TypeScript compiler (`tsc`) to generate fresh `.js` and `.d.ts` files in `./build`.

3. **`npm run pub` (`npm version patch && npm run build && npm publish --access public`)**:
   - **`npm version patch`**: Automatically increments the patch version in `package.json` (e.g., `1.0.3` $\rightarrow$ `1.0.4`).
   - **`npm run build`**: Cleans and rebuilds the TypeScript code with the new version.
   - **`npm publish --access public`**: Uploads the package tarball to the public npm registry.

## 6. What to Do When Updating the Common Library (Step-by-Step Checklist)

Whenever you add a new feature, middleware, error class, or event definition to `common`, follow these 4 steps:

### Step 1: Make your changes in `common/src/`
Add, edit, or remove files inside `common/src/` (e.g. `src/events/ticket-created-event.ts`).

### Step 2: Re-export in `common/src/index.ts`
Ensure any new classes, interfaces, or functions are exported in `common/src/index.ts`:
```typescript
export * from './events/ticket-created-event';
```

### Step 3: Build and Publish the new version
Inside the `common` directory, run:
```powershell
npm run pub
```
This will automatically:
- Bump the version (e.g., `1.0.5` $\rightarrow$ `1.0.6`)
- Clean `./build/`
- Compile TypeScript to JavaScript and `.d.ts` definitions
- Upload the new version to npm

### Step 4: Update Consuming Microservices
In each microservice directory that uses the common package (e.g., `auth`, `tickets`, `orders`):
```powershell
npm update --save @mehul-mrtickets/common
```
*(Or force-install the latest version: `npm install @mehul-mrtickets/common@latest`)*

> [!TIP]
> **Kubernetes / Skaffold Auto-Rebuild**:
> Because `package.json` was updated in the microservice, Skaffold will automatically detect the dependency change, trigger a Docker image rebuild with `npm install`, and restart the Kubernetes pod with the new version.
> If a pod does not restart automatically, you can trigger a restart with:
> `kubectl rollout restart deployment <service-name>-depl` (e.g., `kubectl rollout restart deployment auth-depl`).

## 7. Barrel Export (`index.ts`) vs Deep Subpath Imports

### Can we leave `index.ts` empty and import files individually?
Yes, but here is how both approaches compare:

#### Approach A: Barrel Export via `index.ts` (Recommended)
`index.ts` re-exports everything:
```typescript
export * from "./errors/bad-request-error";
export * from "./middlewares/current-user";
```
Consumers import cleanly in one line:
```typescript
import { BadRequestError, currentUser, validateRequest } from '@mehul-mrtickets/common';
```

#### Approach B: Deep Subpath Imports (Without `index.ts`)
If `index.ts` is empty, consumers must import from the compiled path inside `build/`:
```typescript
import { BadRequestError } from '@mehul-mrtickets/common/build/errors/bad-request-error';
import { currentUser } from '@mehul-mrtickets/common/build/middlewares/current-user';
```

#### Approach C: Clean Category Imports using `exports` in `package.json`
If you want consumers to import by category (e.g. `@mehul-mrtickets/common/errors`), define the `exports` map in `package.json`:
```json
{
  "exports": {
    ".": "./build/index.js",
    "./errors": "./build/errors/index.js",
    "./middlewares": "./build/middlewares/index.js"
  }
}
```
Consumers can then write:
```typescript
import { BadRequestError } from '@mehul-mrtickets/common/errors';
import { currentUser } from '@mehul-mrtickets/common/middlewares';
```

```text
│                           DEVELOPMENT WORKFLOW                              │

    │
    ▼
 2. Re-export it in common/src/index.ts
    │
    ▼
 3. Run: npm run pub (in common/)
    ├── a. npm version patch (Bumps 1.0.5 -> 1.0.6)
    ├── b. del-cli (Wipes old build/)

    └── d. npm publish (Uploads build/ to https://registry.npmjs.org)
    │
    ▼

    Run: npm update --save @mehul-mrtickets/common
    │
    ▼
 5. Import and use cleanly:
    import { BadRequestError, currentUser } from '@mehul-mrtickets/common';
```
